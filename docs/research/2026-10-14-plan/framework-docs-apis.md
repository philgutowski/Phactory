# Phactory external contracts: framework and API research

Date of research: 2026-10-14. Every claim carries a URL and a label. PRIMARY means vendor documentation or a vendor owned repository. THIRD PARTY means anything else. UNVERIFIED means the claim could not be confirmed from a source reachable during this pass. A note on hyphens: this document keeps hyphens only inside code identifiers and URLs, never in prose.

## Headline findings that affect the plan

1. The MCP specification (revision 2026-07-28) now marks Dynamic Client Registration (RFC 7591) as deprecated and names Client ID Metadata Documents (CIMD) as the replacement. DCR is retained for backwards compatibility and is still what Grok uses and what the Claude app falls back to. Phactory's authorization server should implement both, with CIMD advertised so the Claude app picks it. PRIMARY: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration
2. Both the official MCP Python SDK and FastMCP discourage embedding a full authorization server in the MCP server. The official SDK says the embedded provider "predates the AS/RS separation" and "New servers should not reach for it." FastMCP calls its `OAuthProvider` "an extremely advanced pattern that most users should avoid." Phactory can still do it (one operator, needs a consent page that selects a project), but it is swimming against both maintainers. PRIMARY: https://py.sdk.modelcontextprotocol.io/run/authorization/ and https://gofastmcp.com/servers/auth/full-oauth-server
3. Claude Managed Agents mounts GitHub repositories only (`github_repository` resource, `https://github.com/<owner>/<repo>` URLs, other forms rejected). There is no Bitbucket mount. Bitbucket work would go through plain `git` in bash over HTTPS with a credential, and whether a vault `environment_variable` credential can be injected into git's HTTP auth header is UNVERIFIED. PRIMARY: https://platform.claude.com/docs/en/managed-agents/github
4. Bitbucket Cloud merge queues have no public REST API to enqueue a pull request or read queue state. The only way in is the UI button or the "automatically queue when builds pass" setting. A public feature request (BCLOUD-24176, filed 2026-07-16) is at "Gathering Interest" with 5 votes. PRIMARY: https://jira.atlassian.com/browse/BCLOUD-24176
5. GitHub merge queue for private repositories is documented as an Enterprise Cloud feature (plus all public repos owned by organizations). No newer changelog extends it to the Team plan. If the operator's private GitHub repos are on Free, Pro, or Team, native merge queue is not available there. PRIMARY: https://github.blog/changelog/2023-07-12-pull-request-merge-queue-is-now-generally-available/

## Part A. Remote MCP server in Python with OAuth

### A1. Official MCP Python SDK

**Package and version.** PyPI package `mcp`, latest 2.3.0. GitHub release v2.3.0 dated 02 Oct (2026, footer year); v2.2.0 on 07 Sep; a 1.x maintenance line (v1.30.0, 07 Sep) still ships. Python 3.11+ for v2. The docs site states it "documents v2, the current stable release line."
PRIMARY: https://pypi.org/pypi/mcp/json , https://github.com/modelcontextprotocol/python-sdk/releases , https://py.sdk.modelcontextprotocol.io/

**Deprecation watch.** v2.0.0 removed `RFC7523OAuthClientProvider` and renamed client `scopes=` to `scope=`. v2.2.0 added `AuthSettings.validate_token_resource` and warns when it is unset; the docs say 3.0 will make it default `True`. Streamable HTTP idle sessions now expire after 30 minutes on the legacy spec. Nothing in the release notes mentions CIMD support on the server side. PRIMARY: https://github.com/modelcontextprotocol/python-sdk/releases

**Auth module shape (resource server role).**
- `mcp.server.auth.provider`: `TokenVerifier` (protocol with async `verify_token(token) -> AccessToken | None`) and `AccessToken` (fields `token`, `client_id`, `scopes`, `resource`, `subject`, `expires_at`, `claims`).
- `mcp.server.auth.settings.AuthSettings(issuer_url, resource_server_url, required_scopes, validate_token_resource)`.
- `mcp.server.auth.middleware.auth_context.get_access_token()` inside a tool.
- Construct `MCPServer(name, token_verifier=..., auth=AuthSettings(...))`; passing only one of the two raises `ValueError`. Run with `mcp.run(transport="streamable-http")`. The SDK then serves `/mcp` and the RFC 9728 document at `/.well-known/oauth-protected-resource/mcp`, and answers unauthenticated requests with 401 plus a `WWW-Authenticate` header pointing at that document.
- `validate_token_resource=True` rejects any token whose `AccessToken.resource` differs from `resource_server_url`. This is the RFC 8707 audience check the spec requires.
- The shipped example verifier is `IntrospectionTokenVerifier` (RFC 7662 introspection against a real AS), described as "the shape most production verifiers take."
PRIMARY: https://py.sdk.modelcontextprotocol.io/run/authorization/

**Authorization server role.** The SDK still accepts `auth_server_provider=` which "embeds a full authorization server inside your MCP server," but the docs say it "predates the AS/RS separation" and "New servers should not reach for it." It provides no login page, consent screen, or token issuance UI. Expectation: Phactory is a resource server and delegates to an external AS (Auth0, WorkOS AuthKit, Keycloak, Cloudflare) or runs its own AS as a separate concern. PRIMARY: https://py.sdk.modelcontextprotocol.io/run/authorization/

**What the spec says about roles (revision 2026-07-28).**
- "A protected MCP server acts as an OAuth 2.1 resource server." The authorization server "may be hosted with the resource server or a separate entity."
- MCP servers MUST implement RFC 9728 Protected Resource Metadata. Authorization servers MUST provide RFC 8414 metadata or OIDC Discovery.
- Authorization servers and clients SHOULD support CIMD and MAY support DCR; "Dynamic Client Registration is deprecated and retained for backwards compatibility."
- PKCE is required (OAuth 2.1). Clients MUST send RFC 8707 `resource` on both authorization and token requests, set to the server's canonical URI (path components allowed, e.g. `https://mcp.example.com/server/mcp`). Servers MUST validate the token was issued for them as audience.
- Servers SHOULD include `scope` in the 401 `WWW-Authenticate` challenge; clients treat it as authoritative. A 403 with `error="insufficient_scope"` drives step up authorization.
PRIMARY: https://modelcontextprotocol.io/specification/latest/basic/authorization and https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration

**CIMD requirements for an AS (if Phactory runs its own).** Fetch the metadata document when `client_id` is an HTTPS URL, validate `client_id` equals the URL exactly, validate `redirect_uri` against the document, cache per HTTP headers, and advertise `"client_id_metadata_document_supported": true` in AS metadata. PRIMARY: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration

### A2. FastMCP (jlowin)

**Version.** PyPI `fastmcp` 4.1.0 ("Fourth and One", GitHub release 08 Oct). v4.1.0 has a Breaking Changes section (HTTP session idle timeouts, Python 3.15) and auth changes: `MultiAuth` now qualifies client IDs by source, token introspection audiences became configurable, browser OAuth clients register as public clients. PRIMARY: https://pypi.org/pypi/fastmcp/json , https://github.com/jlowin/fastmcp/releases

**Auth providers.**
- `TokenVerifier` / `JWTVerifier`: validate tokens only, no discovery metadata.
- `RemoteAuthProvider`: token validation plus OAuth discovery metadata for an external IdP that supports DCR (WorkOS AuthKit via `AuthKitProvider`, Descope named).
- `OAuthProxy` (and `GitHubProvider`, Google, Azure, AWS variants): presents a DCR compliant registration endpoint to clients while using fixed upstream credentials at a provider that lacks DCR.
- `OAuthProvider`: full OAuth 2.1 authorization server inside the MCP server. Abstract methods: `get_client`, `register_client`, `authorize`, `load_authorization_code`, `exchange_authorization_code`, `load_refresh_token`, `exchange_refresh_token`, `load_access_token`, `revoke_token`, `verify_token`. The page calls it "an extremely advanced pattern that most users should avoid," reserved for cases like air gapped or special compliance. It has a `register_client` hook (so DCR is possible) but the page does not name RFC 7591 or CIMD. UNVERIFIED whether FastMCP 4 implements CIMD on the AS side.
- `MultiAuth` composes an optional OAuth server with verifiers.
PRIMARY: https://gofastmcp.com/servers/auth/authentication and https://gofastmcp.com/servers/auth/full-oauth-server

**Reasonable for one operator?** Yes if Phactory delegates to an external AS: `RemoteAuthProvider` or `AuthKitProvider` is a few lines and gets DCR from WorkOS. Marginal if Phactory wants to be its own AS: `OAuthProvider` gives a skeleton but every storage and consent concern is yours, and the maintainers say avoid it. The official SDK is the thinner dependency; FastMCP adds the provider catalogue and `OAuthProxy`. Either works with Streamable HTTP. THIRD PARTY judgment on the vendor facts above.

### A5. Binding a token to one project

**What the spec allows.**
- RFC 8707 `resource`: clients MUST send the server's canonical URI; path components are legitimate when they identify an individual server. The AS binds the token audience to that URI; the RS MUST reject tokens for another audience. PRIMARY: https://modelcontextprotocol.io/specification/latest/basic/authorization
- Scopes: the RS advertises required scopes in the 401 challenge and `scopes_supported`; the AS consent page decides what is granted. Clients request what the server tells them; neither the Claude app nor Claude Code offers the user a scope picker. PRIMARY: https://www.claude.com/docs/connectors/building/authentication
- With DCR each client registration is anonymous and per connection, so client identity cannot carry project identity. CIMD gives a stable client identity (Claude, Grok) but still not a project. PRIMARY: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration

**Two candidate mechanisms.**
1. One MCP URL per project, e.g. `https://phactory.example/mcp/<project>`. Each URL serves its own RFC 9728 document with `resource` set to that exact URL. The client sends `resource=<that URL>`, the AS issues a token with that audience, and the RS checks `validate_token_resource`. Project identity is the audience. Works with an external AS as long as it supports RFC 8707 resource indicators or an equivalent audience parameter. Both the Claude app and Grok can express this today, because each connector is just a URL. The cost is one connector per project in each client.
2. One MCP URL, project chosen at consent. Phactory's own AS renders a consent page with a project selector and encodes the project as a scope or claim in the token. Both clients can express this, because the consent page is just a browser page in the OAuth redirect. The cost is that Phactory must be the AS (or at least own the consent UI), and a user who wants two projects needs two connections to the same URL, which the Claude UI does not obviously support (one custom connector per URL, UNVERIFIED).

**Smallest mechanism.** Option 1. It keeps Phactory a plain resource server, uses only what the spec already requires (resource indicators plus audience validation), and needs no custom consent page. The spike should prove that the Claude app and Grok each send `resource` equal to the project URL and that a token for project A is rejected (401) at project B's URL.

## Part B. Claude Managed Agents

- Four primitives: Agent (model, system prompt, tools, MCP servers, skills), Environment (cloud sandbox or self hosted), Session, Events. Vaults hold credentials; scheduled deployments and memory stores are adjacent. Status: beta. All endpoints need header `anthropic-beta: managed-agents-2026-04-01`; the SDK sets it. Enabled by default for all API accounts. PRIMARY: https://platform.claude.com/docs/en/managed-agents/overview
- Endpoints: `POST /v1/agents`, `POST /v1/environments`, `POST /v1/sessions`, `POST /v1/sessions/{id}/events`, `GET /v1/sessions/{id}/events`, `GET /v1/sessions/{id}/events/stream`, `POST /v1/sessions/{id}/archive`, `DELETE /v1/sessions/{id}`. PRIMARY: https://platform.claude.com/docs/en/managed-agents/session-operations and https://platform.claude.com/docs/en/managed-agents/events-and-streaming
- Python SDK: `anthropic` 1.14.0 latest on PyPI, requires Python >= 3.10. PRIMARY: https://pypi.org/pypi/anthropic/json

### B2. Retrieving the event log after a session ends

- "Event history is persisted server-side and can be fetched in full." `GET /v1/sessions/{session_id}/events` returns the full history; filter with `types[]=agent.tool_use&types[]=agent.tool_result`. Pagination is cursor based (`limit`, `page`, `next_page`); the session list documents `prev_page` as well, and the SDK page object auto paginates forward. PRIMARY: https://platform.claude.com/docs/en/managed-agents/overview , https://platform.claude.com/docs/en/managed-agents/events-and-streaming , https://platform.claude.com/docs/en/managed-agents/session-operations

- Cost: `session.usage` carries `list_cost` (`{amount, currency}` in cents as an integer string) and `active_seconds`; the session object's `usage` field has the same totals. Per model request cost is not emitted, only tokens in `span.model_request_end.model_usage`. PRIMARY: https://platform.claude.com/docs/en/managed-agents/reference ; cents encoding PRIMARY: https://platform.claude.com/docs/en/managed-agents/budgets
- Retention: "Conversation history is preserved unless the session is explicitly deleted." Sandbox state is preserved only 30 days after creation. The data retention page says "session transcripts persist until you delete them." No documented auto expiry of events. PRIMARY: https://platform.claude.com/docs/en/managed-agents/events-and-streaming and https://platform.claude.com/docs/en/manage-claude/api-and-data-retention
- Webhooks exist for session status with slightly different names (`session.status_idled`). PRIMARY: https://platform.claude.com/docs/en/managed-agents/reference

### B3. Getting a git repository into the session

- Mechanism: a session `resources` entry of `type: "github_repository"` with `url` (`https://github.com/<owner>/<repo>`, no `.git`, SSH and other forms rejected with `invalid_request_error`), `authorization_token` (GitHub PAT, never echoed), optional `mount_path` (default `/workspace/<repo>`) and `checkout` (branch or commit). Cloned before the agent starts; cached across sessions; multiple repos allowed; token rotatable mid session via `sessions.resources.update`. Token scopes: `repo` for private clone and PR creation. PRIMARY: https://platform.claude.com/docs/en/managed-agents/github
- Auth path: `git pull` and `git push` on the mounted repo go through an Anthropic side git proxy that injects the token after the request leaves the sandbox; the token is never inside the container. PRIMARY (Anthropic skill docs shipped with Claude Code, mirroring platform docs): https://platform.claude.com/docs/en/managed-agents/github
- Creating a PR needs the GitHub MCP server (`https://api.githubcopilot.com/mcp/`) with its credential in a vault; the repo resource gives filesystem and git only. PRIMARY: https://platform.claude.com/docs/en/managed-agents/github
- There is no GitHub App connection; it is PAT based. UNVERIFIED whether a fine grained PAT works for the git proxy (docs recommend fine grained tokens, so likely yes).
- Bitbucket Cloud: no mount type. Under `limited` networking with `allow_package_managers: true`, `bitbucket.org` is on the reachable host list (so is `gitlab.com`), so `git clone https://bitbucket.org/...` can run in bash. The credential path is the open question: vault `environment_variable` credentials are substituted at egress into request headers and body only, never URL paths, and only for hosts in the credential's `allowed_hosts`. A `git -c http.extraHeader="Authorization: Basic <placeholder>"` form would put the placeholder in a header, which is the substitution location, but nothing documents git over HTTPS with a vaulted credential to a non GitHub host. UNVERIFIED and must be the spike's fact. The insecure fallback (pasting an app password into the session) works but violates the vault model. PRIMARY: https://platform.claude.com/docs/en/managed-agents/environments (package manager hosts table and the warning that an allowed host permits `git push`) and the vault substitution rules summarized from https://platform.claude.com/docs/en/managed-agents/vaults (UNVERIFIED exact URL; the rules were read from Anthropic's bundled skill documentation).

### B4. System prompt, tool set, restrictions

- `system` is set on the agent; it is fixed for the session's lifetime; a session can override `model`, `system`, `skills` at creation. Mid session, only `agent.tools` and `agent.mcp_servers` can change, and only while idle. `system.message` events append system context on supported models. PRIMARY: https://platform.claude.com/docs/en/managed-agents/session-operations
- Tools: `agent_toolset_20260401` exposes `bash`, `read`, `write`, `edit`, `glob`, `grep`, `web_fetch`, `web_search`. Use `default_config: {enabled: false}` and enable only `bash`, `read`, `write`, `edit`, `glob`, `grep` to get no web tools. Each tool accepts a `permission_policy` (`always_allow`, `always_ask`, `auto`). Custom tools (`type: "custom"`) are executed by your application. PRIMARY: https://platform.claude.com/docs/en/managed-agents/tools
- Network: environment `networking` is `unrestricted` (default if omitted, with a safety blocklist) or `limited` (deny by default, `allowed_hosts`, `allow_package_managers`, `allow_mcp_servers`). "No network except git" is expressible as `limited` with `allowed_hosts: ["github.com"]` (or `allow_package_managers: true` for the whole code host and registry list). Warning in the docs: access is per host, not per operation, so an allowed host permits `git push` with any credential the command supplies. Mounted GitHub repos stay reachable even with no hosts allowed. PRIMARY: https://platform.claude.com/docs/en/managed-agents/environments

### B5. Pricing and rate limits

- Two billing dimensions: tokens at model list rates plus session runtime at $0.08 per session hour, measured to the millisecond, accrued only while `running` (not `idle`, `rescheduling`, `terminated`). Web search $10 per 1,000. No container hour charge on top. Batch discount does not apply. PRIMARY: https://platform.claude.com/docs/en/about-claude/pricing
- Rate limits per organization: create endpoints (agents, sessions, environments) 300 requests per minute; read endpoints 1,200 per minute. Organization spend limits and usage tier limits also apply. PRIMARY: https://platform.claude.com/docs/en/managed-agents/reference
- Session budgets: optional hard cap `budget.max_list_cost` in cents; the session pauses idle with `stop_reason: budget_reached`. PRIMARY: https://platform.claude.com/docs/en/managed-agents/budgets

### B6. Zero data retention

Confirmed not eligible. "Managed Agents is not currently eligible for Zero Data Retention or HIPAA Business Associate Agreement coverage." The feature eligibility table lists `/v1/agents`, `/v1/sessions`, `/v1/environments` as ZDR No, HIPAA No, with the note "Sessions are stateful resources; transcripts persist until you delete them," applying to all sub features including self hosted sandboxes. PRIMARY: https://platform.claude.com/docs/en/managed-agents/overview and https://platform.claude.com/docs/en/manage-claude/api-and-data-retention

## Part C. Merge queues

### C1. GitHub merge queue

**Enqueue by API.**
- GraphQL `enqueuePullRequest(input: {pullRequestId: ID!, expectedHeadOid: GitObjectID, jump: Boolean, clientMutationId})` returns `mergeQueueEntry`. `dequeuePullRequest(input: {id: ID!})` removes it. PRIMARY: https://docs.github.com/en/graphql/reference/pulls
- REST: `PUT /repos/{owner}/{repo}/pulls/{pull_number}/merge-async` with `merge_action: "merge_queue"` "adds the pull request to a merge queue"; an `enqueued` result is final and does not mean merged. The synchronous merge endpoint does not support queues. PRIMARY: https://docs.github.com/en/rest/pulls/pulls?apiVersion=2022-11-28

**Read queue state.** GraphQL `PullRequest.mergeQueueEntry` (fields `state` in AWAITING_CHECKS, LOCKED, MERGEABLE, QUEUED, UNMERGEABLE; `position`, `enqueuedAt`, `estimatedTimeToMerge`, `headCommit`, `baseCommit`, `solo`, `jump`), `PullRequest.isInMergeQueue`, `PullRequest.mergeQueue` with `entries` connection, `nextEntryEstimatedTimeToMerge`, and `configuration` (`mergeMethod`, `mergingStrategy`, `maximumEntriesToBuild`, `maximumEntriesToMerge`, `minimumEntriesToMerge`, `minimumEntriesToMergeWaitTime`, `checkResponseTimeout`). PRIMARY: https://docs.github.com/en/graphql/reference/pulls

**Which commit lands.** The docs say the queue creates temporary branches `gh-readonly-queue/{base_branch}/pr-{n}-{sha}` that "contain a different sha from the pull request," runs required checks via the `merge_group` event (`checks_requested`), and once checks pass "the temporary branch will be merged in to the target branch." The merge method is the queue's configured merge, squash, or rebase. The docs never state in one sentence that the base branch is fast forwarded to the tested `merge_group.head_sha`. PRIMARY: https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue ; GitHub Actions docs: `GITHUB_SHA` for a `merge_group` run is "SHA of the merge group." PRIMARY: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows
- THIRD PARTY statements that the merge group head is exactly what lands: Buildkite's tutorial ("the exact commit that will end up on the target branch if the merge group is successfully merged") https://buildkite.com/docs/pipelines/tutorials/github-merge-queue , and a repository PR noting "after the queue fast-forwards main to the group head" https://github.com/eshu-hq/eshu/pull/7283 . Treat as UNVERIFIED until the spike compares `merge_group.head_sha` with the base branch tip after merge.
- Webhook example payload (octokit, GitHub owned repo): `merge_group.head_sha`, `head_ref` = `refs/heads/gh-readonly-queue/main/pr-104-<sha>`, `base_sha`, `base_ref` = `refs/heads/main`, `head_commit.message` = "Merge pull request #2048 ...". PRIMARY (GitHub owned): https://raw.githubusercontent.com/octokit/webhooks/main/payload-examples/api.github.com/merge_group/checks_requested.payload.json

**Ruleset and required checks.** "Require merge queue" is a branch protection rule and ruleset rule; after required CI passes, "GitHub merges the pull request using the merge strategy set in the branch protection rule." Workflows that back required checks must add `on: merge_group` (`checks_requested`); it is separate from `pull_request` and `push`. The detailed queue settings list (build concurrency, group size, wait time, timeout) was not present in the rendered rulesets page; UNVERIFIED by this pass but mirrored by the GraphQL `MergeQueueConfiguration` fields above. 1. Agent surface: build a Streamable HTTP resource server with the official `mcp` 2.x SDK (`MCPServer(token_verifier=..., auth=AuthSettings(validate_token_resource=True))`), one URL per project, and put the authorization server behind it as a separate component that supports DCR plus CIMD and PKCE S256. Spike must prove: Grok's DCR `POST /register` (redirect `https://grok.com/connectors-oauth-exchange-code/`) and the Claude app's CIMD flow (callback `https://claude.ai/api/mcp/auth_callback`) both complete, and a token minted for project A's URL is refused at project B's URL.
2. Authorization server choice: default to an external AS that supports DCR, CIMD, and RFC 8707 (WorkOS AuthKit or Keycloak) unless the spike shows one of the two clients needs a consent page Phactory controls. Spike fact: the external AS honours the `resource` parameter and emits it as token audience.
3. Builder: Claude Managed Agents, beta header `managed-agents-2026-04-01`, `anthropic` 1.14.0, agent with `default_config.enabled: false` and only bash plus file tools, `limited` networking, and the full event log read from `GET /v1/sessions/{id}/events` as the trace. Spike must prove: a finished session's events list contains every `agent.tool_use`, `agent.tool_result`, `span.model_request_end.model_usage`, and the final `session.usage.list_cost`, retrievable after `archive`.
4. Builder repo access: GitHub via `github_repository` resource with a PAT and a `checkout` branch; Bitbucket only if the spike proves a vaulted `environment_variable` credential is substituted into git's HTTP auth header on `bitbucket.org` under `limited` networking. If it fails, Bitbucket builds get a Phactory side push step (session writes a patch or bundle to outputs, Phactory pushes).
5. Merge path, GitHub: use `enqueuePullRequest` (or `merge-async` with `merge_action: merge_queue`) and read `mergeQueueEntry.state`; land detection from `pull_request` closed with `merged: true` and `merge_commit_sha`. Spike must prove the operator's private repo plan actually offers merge queue, and whether `merge_group.head_sha` equals the base tip after merge.
6. Merge path, Bitbucket Cloud: there is no enqueue API, so the plan must either rely on the "automatically queue when builds pass" setting plus the `pullrequest:fulfilled` webhook (`pullrequest.merge_commit.hash`), or drop native queues for Bitbucket. Spike must prove auto queue triggers without a human click and report which SHA lands.
7. Tracker side effects: Jira "Pull request merged" trigger keyed on the issue key in branch name or PR title, so Phactory must put the key in both; GitHub Projects moves the PR item itself and moves the issue only through "Item closed" after a default branch merge with a closing keyword.
8. Budget and retention assumptions: $0.08 per running session hour plus tokens; events persist until deleted, sandboxes 30 days; no ZDR. Plan deletion of sessions as Phactory's retention control.
