# Agent native assessment: Phactory first version

Sources read: the first version plan (R1 to R35, AE1 to AE8), the software factory ideation note, the xAI surface research, the manager agents research, plus the grounding dossier pointers for the lifted status read and handoff shape.

## Applicability

Agents are first class users of this plan, and the plan already says so. R25 makes every verb agent callable, A2 names the manager agent as the actor that files cards and drives verbs, and AE4 and AE8 are agent only acceptance examples. The question is not whether to plan for agents but which verbs an agent may touch now, what an agent must be able to see to do the two jobs the plan gives it (file a good card, answer "what is being built" by voice), and where agent reach must stop so the host stays the only approval authority.

Verb classification for agent access over MCP:

| Verb | Agent access | Reason |
|---|---|---|
| onboard | Now | R29, R33, AE8 require it. Needs a bootstrap token answer (see Open Questions). |
| dispatch | Now, idempotent, within cap | The manager agent's core action after filing a card. Spends an account, so it carries the heaviest audit and guard. |
| status | Now | The read every other agent job depends on. Composed form for voice, atomic reads beside it. |
| land | Now as idempotent retry only | Pushes the branch and opens or re enqueues the pull request. Never approves, never merges. |
| eval | Now for reads. Later for reruns of the judged score from a project token | Reads cost nothing. A rerun spends a judge account and is the replay tuning tool the operator uses from the terminal first (Success Criteria). |
| trace | Now, read only | Returns the Langfuse trace link and a summary, scoped by token. |
| watch | Now as a cursor read of events. Later as push delivery | No consumer MCP client is known to receive server notifications. Spike three decides the Later half. |

Nothing found breaks a settled decision. One settled decision needs a refinement to work: a token scoped to one project cannot onboard a project that does not exist yet. The fix keeps the decision intact and is in Key Technical Decisions.

## Planning Changes

### Requirements

Additions and sharpenings the planner should carry into the contract.

1. **Project identity comes from the token, never from a parameter.** No MCP tool accepts a project id. The server derives the project from the token and every read and write is bounded by it. This is the mechanism behind R27 and AE4, and it removes the whole class of "agent passed the wrong project" bugs. A lookup for a card, build, or trace that belongs to another project returns not found, not forbidden, so the existence of other customers' work does not leak.
2. **Every mutating verb is idempotent on the card key.** Dispatching the same card twice returns the first build. Land on a card whose pull request already exists returns that pull request. This is the carried rule "two systems landing the same card is the worst failure" applied to a manager agent that repeats itself, which agents do. Belongs beside R5 and R9.
3. **Every tool result carries actor, state, and the next human step.** R8 says identity is recorded; the agent facing version is that every result names who caused the state, what state the card is in, and the host link where a person acts if one is needed. This is what lets a voice agent say "it is waiting on you, the link is on your page" without a second call.
4. **Onboard over MCP never carries a secret.** Account questions are answered by name from the operator file (R3). The server rejects anything that looks like a key or password as an answer. A voice conversation on a phone is the worst place for a credential to transit, and the project file must never hold one.
5. **A draft card check is in scope as a read only tool.** The plan defers "whether Phactory offers a check that a draft card has a usable definition of good before the manager agent files it". Decide yes. Phactory never writes the tracker, so the only lever it has on card quality before dispatch is to tell the manager agent whether the draft would dispatch: label recognised, definition of good present and in the shape the deterministic score can read (named test, declared paths), no collision with files in flight. Without it the first time a bad card is caught is after a builder has spent an account on it.
6. **R31 over MCP is a handoff, not a write.** The trivial card that closes onboarding has to be filed on the tracker, and Phactory never writes the tracker. Onboard's final step therefore returns the card to file (label, title, definition of good) and asks the caller to file it and then call dispatch. In the terminal the operator files it. Over MCP the manager agent files it with its own tracker access. Make this explicit in R31 or AE8 so the parity test does not expect Phactory to file anything.

### Key Technical Decisions

**Tool list for the MCP server.** Atomic verbs with rich results, named by what they do to a card.

* `status()` composed. Returns counts (building, waiting to land, needs you, halted, landed today), the per card list with state, actor, started at, builder, pull request link, and a `spoken` field holding one sentence the agent can read aloud. One call, one spoken answer. This is the voice tool.
* `project_rules()` read. Allowed lane labels with one line meanings, the definition of good template the deterministic score reads, declared paths convention, the done line convention, machine bound tests, cap, free slots. This is what a manager agent needs before it files a card and what it did not have in either earlier system.
* `check_card(draft)` read, no side effect. Returns would dispatch or the list of what is missing. Requirement 5 above.
* `card(key)` read. Full state of one card: build id, builder, provider session id, branch, commit, pull request link, gate result, verify result, scores, trace link, halt evidence, every recorded actor. The atomic read behind status.
* `in_flight()` read. Files each in flight build is editing, branch names, base commits. The cross build fact the handoff already carries (R10), exposed so the manager agent can steer the next card away from a collision.
* `dispatch(card_key)` write, idempotent. Refuses a card without a lane label (R9), a card already owned by a build, and a project at cap (R5). Returns build id, state, actor. Account and model come from the project file (R13); the agent cannot choose them.
* `land(card_key)` write, idempotent retry. Pushes the returned branch if not pushed, opens the pull request if none, re enqueues if the queue dropped it. Returns pull request link and state. It has no approve or merge path, by construction, not by permission.
* `eval(card_key)` read in the first version. Returns both scores kept apart (R24) and the rubric result. A rerun flag is terminal only for now.
* `trace(card_key)` read. Returns the Langfuse link and a short summary (tool calls, files changed, commands run, outside connections).
* `events(since)` read, cursor based. Ordered state transitions for the project since a cursor. This is watch over MCP in the first version.
* `onboard_start()`, `onboard_answer(session_id, question_id, answer)`, `onboard_status(session_id)`. Shape below.

No workflow tool is needed for safety. The one sequence that is safety critical, approve then merge then verify, is owned by the host and the workflow engine, not by any tool an agent can call. The sequence an agent does run, check then dispatch, is two calls on purpose: the check is free and the dispatch spends money, and an agent should see the gap.

**Action parity.** Human only, with no agent tool: approving a pull request (R19, host app), editing a project file outside onboard (F4, a config edit by the operator), writing a definition of good (the card's author owns the standard; the agent drafts, the person who files it is accountable), and rerunning the judged score during tuning. Agent tools exist for: filing a card (outside Phactory, on the tracker), checking a draft, dispatching, retrying land, reading everything, and onboarding. An agent must not be able to approve anything through Phactory. If the manager agent holds host credentials of its own and approves a pull request there, that is outside Phactory's control, but Phactory records the approval as "approved in host by <host user>" and never as approved by the agent, because Phactory reads the approval from the host (R20) and holds none itself (R28).

**Context parity.** To file a good card a manager agent needs `project_rules` and `in_flight` plus the last few landed cards with their scores from `status`, so it learns what the judge rewarded. To answer "what is being built" by voice it needs one composed `status` call whose `spoken` field is already a sentence, because a voice agent reading five rows aloud is not an answer. Atomic reads exist for the agent's own reasoning between turns; the composed read exists for the person on the phone. Both are projections of the same workflow state and must never disagree, so build the composed read from the atomic ones in one request, not from a separate cache.

**Execution lifecycle.** `dispatch` returns immediately with a build id and the state `handoff_written`. The workflow engine advances the build through states that `status` and `card` expose as partial progress: handoff written, builder started (provider session id), branch pushed (commit), pull request opened (link), gate running, gate green or red, waiting for operator, merged, verifying, halted with evidence, trace exported, scored. Completion reaches an agent two ways. In the first version, by the agent calling `events(since)` or `status` on the next turn when the person asks; this is a pull by the agent on a human cadence, not polling by a builder, and it is the honest answer for consumer apps today. Later, by push, if spike three shows a client that receives MCP server notifications or if the platform exposes a webhook into the manager (Grok Automations and Claude scheduled tasks are both unverified in the research). The plan's "remote builders never poll" rule applies to builders waiting on a card comment, and the hosted builder path already satisfies it because the workflow starts the session and the session ends on its own. The gap the plan has not named is the operator: when a card reaches needs you at two in the morning, nothing in R28 tells him. The page is pull. See Open Questions.

**Onboard over MCP.** One session, one state machine, two front ends. `onboard_start()` returns a session id and the first question. Each question carries an id, the text, choices when a choice exists (hosts, trackers, boards the adapter can list, accounts by name from the operator file, builders, auto merge on or off), whether free text is allowed, a default when one is safe, and one line on why it is asked. `onboard_answer` returns the next question, or a property check result with its single next step (R30), or done with the card to file (R31 handoff). `onboard_status` returns the session's answers so far, so a dropped phone call resumes and so R32 re entry works the same way. The terminal wizard is a client of the same three calls, which is how AE8 is made true rather than tested for.

The hazard is an agent that fabricates answers. In voice, a manager agent asked "what is the gate command" by Phactory will answer the person's question for them if it thinks it knows, and it will pick a plausible account name or invent a board. Four guards, in order of value. First, closed choices wherever the adapter can enumerate the real options, so a fabricated board or account is rejected at the answer, not discovered later. Second, every answer recorded with actor as "agent <client> on behalf of operator", so a wrong answer has a visible origin. Third, no secret ever passes through the wizard (Requirement 4). Fourth, the trivial card at the end (R31) is the only proof the free text answers were true: a fabricated gate command fails there, before any real card. Make the wizard return to the failing question with the failure output rather than marking the project ready. AE6 already covers a missing gate; add the case where the gate command is wrong.

**Trust and control.** Verbs that are irreversible or spend money: `dispatch` spends an account and starts hours of work; `land` pushes to a customer's repository and opens a pull request their team can see; `eval` rerun spends a judge account; `onboard_answer` on finish writes a project file. Reads cost nothing. The fitting shape for one operator with identity recorded is an audit row on every mutating call, not an approval inbox. The row holds the operator (OAuth subject), the client (the client id from dynamic client registration, with the name it registered under, so "grok bot for Acme" is a readable actor), the project, the tool, the arguments, the time, and the result. Guards without an inbox: idempotency on card key (Requirement 2), the per project cap (R2, R5), and one addition the planner should take, a per project per day dispatch count in the project file, so a looping agent cannot spend a day's budget in an hour. If a customer later wants a human go before any dispatch, the project file can gain a flag that parks MCP dispatches under needs you; do not build that in the first version, only leave the state for it.

### Implementation Units

Where this lens changes the unit list or its order.

1. **MCP server unit should ship with `status`, `project_rules`, `card`, `in_flight`, `events`, and `trace` as reads first**, then `dispatch` and `land` as writes, then the three onboard calls. Reads prove isolation (AE4) before any write exists.
2. **Onboard unit is one state machine with two front ends**, and the terminal front end is the second client of it, not the first implementation. If the terminal wizard is built first as its own loop, AE8 becomes a diff test that keeps failing.
3. **The OAuth unit needs a consent step that picks the project**, and for onboard, reserves a new project id so a token exists for a project with no file yet (Key Technical Decisions, bootstrap). This is a small addition to the OAuth unit, not a new unit.
4. **The workflow engine unit must expose state transitions as a readable event log per project** from the start, because `events`, `status`, the page, and any later push all read it. If the engine's own history is the only record, every surface pulls from the engine and the engine becomes the bottleneck the laptop used to be.
5. **`check_card` lives in the deterministic score unit**, because it reads the same definition of good shape the score reads. One parser, two callers.
6. **Spike three grows by two checks**: whether the client ever receives an MCP server notification while a tool is not running, and whether the client supports the MCP tasks pattern for long calls. Both decide watch's Later half and cost nothing extra once the stub server is registered.

### System Wide Impact / Risks

* **Token for a project that does not exist.** Without the bootstrap answer, onboard over MCP cannot start, and R33 and AE8 fail at the first call. Highest architectural risk in this lens.
* **Existence leak across customers.** A not found that differs from a forbidden, or an error message that names another project's card key, breaks AE4 in a way the happy path test never sees. The isolation test must probe another project's ids on purpose.
* **Composed status drifting from atomic reads.** If `status` is a cache and `card` is live, a voice answer will be wrong at the exact moment it matters. Build one from the other in the same request.
* **Dispatch repeats.** Agents retry on any ambiguity. Without idempotency on card key, a flaky network spends two accounts and opens two pull requests for one card, the exact failure the earlier systems called the worst one.
* **Secrets in the onboard path.** A phone conversation is the weakest link for credential hygiene in the whole design. The rejection has to be server side.
* **Operator notification is absent.** Needs you is a state on a page nobody is looking at while the laptop is closed. A full day with the laptop closed (Success Criteria) is also a full day of approvals nobody knows about. Not an MCP problem, but this lens exposes it because the agent cannot deliver it either.
* **Langfuse links cross the boundary.** A `trace` result hands the agent a link into Langfuse. If Langfuse holds every project in one workspace, that link, or the agent's Langfuse access behind it, is a second path to another customer's traces. R27 names traces explicitly. Either one Langfuse project per Phactory project with per project keys, or `trace` returns a summary and the link is operator only.

### Verification

Agent native scenarios, each with input, action, expected outcome.

1. **Two customer isolation (AE4, extended).** Input: projects A and B each with two cards in flight and one landed, a token scoped to A. Action: `status`, then `card(B card key)`, `trace(B card key)`, `dispatch(B card key)`, `events` from cursor zero. Expected: `status` and `events` list only A's cards; the three B lookups return not found with no mention of B's key, project name, or existence; the audit log shows the three refused calls against A's project; the Langfuse link returned for A's landed card opens nothing of B.
2. **Onboard parity (AE8, extended).** Input: the same scripted answers for a GitHub repository with a Projects board. Action: run the terminal wizard, then run `onboard_start` and `onboard_answer` over MCP. Expected: the sequence of question ids, texts, and choice lists is identical; the two project files are identical except the recorded actor; both end with the same trivial card returned to file, and neither writes the tracker.
3. **Fabricated onboard answer.** Input: a repository whose gate is `pytest`. Action: over MCP, answer the gate question with `npm test`, answer the account question with a literal key string. Expected: the key string is rejected at `onboard_answer` with the list of account names as choices; the gate answer is accepted as free text, the trivial card dispatches, the gate fails, and onboard returns to the gate question with the failure output; the project file is not marked ready; the audit row names the agent client as the answerer.
4. **Idempotent dispatch.** Input: one labelled card, a project with free slots. Action: `dispatch` three times within a minute from the same client, then once from the terminal. Expected: one build, one builder session, one pull request; calls two through four return the first build id and its current state; the audit log has four rows and one dispatch.
5. **Completion without polling.** Input: a card dispatched over MCP, then the client disconnects. Action: hours later, `events(since the dispatch cursor)` then `status`. Expected: `events` returns the ordered transitions from handoff written through scored with actor on each; `status` shows the card as landed with both scores and the merged commit equal to the tested commit; no call was made between dispatch and completion.
6. **Agent cannot approve.** Input: a project with auto merge off, a card whose gate is green and pull request awaits approval. Action: over MCP, `land(card key)`, then every tool in the list with any arguments touching approval. Expected: `land` returns waiting for operator with the host link and changes nothing; no tool accepts an approval argument; after the operator approves in the host app, `card` records approved by the operator's host user, never by the agent (AE1 shape).
7. **Refusals with reasons.** Input: project cap two, two builds in flight, one labelled card and one unlabelled card. Action: `dispatch` each. Expected: the labelled card is refused with reason at cap and the two in flight cards named; the unlabelled card is refused with reason no lane label and the allowed labels listed; `check_card` on the unlabelled draft returns the same missing item before dispatch is attempted.
8. **Voice answer is one sentence.** Input: a project with three building, one waiting to land, one halted. Action: `status`. Expected: the `spoken` field is one sentence naming the three counts and that one card needs the operator, and the per card list under it agrees with `card` on every state; the halted card's entry carries the host link and the evidence summary.

### Scope Boundaries

* **In scope by this lens:** the eleven tool shapes above, idempotency on card key, project from token, the `check_card` read, the per day dispatch count, the onboard bootstrap token, the two spike three additions.
* **Out of scope, confirm as deferred:** push delivery of completion to a consumer app (watch Later), judged score reruns from a project token, an approval inbox inside Phactory, an operator wide MCP token for the across projects view (the page serves that in the first version), a dispatch requires operator flag.
* **Never, by identity:** an agent approving or merging through Phactory; Phactory writing the tracker on an agent's behalf, including the trivial onboarding card.

## Open Questions

1. **How does an agent hold a token for a project that does not exist yet?** Proposed: the OAuth consent screen offers new project, reserves a project id, and mints a token scoped to it before the first onboard question. Keeps the one project per token decision intact. Must be settled before the MCP and onboard units are sequenced, since both depend on it.
2. **How does the operator learn a card needs him while the laptop is closed?** R28 is a page, pull only. The agent cannot deliver it. Decide whether the first version adds one outbound notification adapter on the needs you transition (the cheapest thing that lets the laptop closed day in Success Criteria be true), or whether that is a later area. Affects the workflow engine unit's transition hooks.
3. **Does any consumer MCP client receive server notifications or support long running tool patterns?** Decides whether watch is cursor only for the first version or gets a push half. Add to spike three. Affects watch's shape and nothing else, so it can be decided late.
4. **Who files the trivial onboarding card over MCP, and with what tracker access?** Phactory never writes the tracker, so the manager agent needs its own. For a project where the agent has none yet, onboard ends with an instruction the operator fulfils by hand. Affects R31's acceptance wording and whether AE8 can run unattended.
5. **Is Langfuse one workspace or one project per Phactory project?** R27 names traces as isolated. The answer decides whether `trace` may return a link to an agent or only a summary. Affects the trace unit and the AE4 test.
