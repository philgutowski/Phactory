# Durable engine and sandbox research for Phactory

Date checked: 2026-10-14. Every claim carries a URL and a label. PRIMARY means the vendor's own docs, repo, or package index. THIRD PARTY means anything else. UNVERIFIED means I looked and could not confirm it from a source I could read.

Phactory's shape, restated so the findings can be read against it: one workflow per card, a builder step of minutes to hours, then a wait of hours to days for a pull request to merge (a human may need to approve), then verify, trace export, score. Many cards in flight per project up to a cap, landing serialised per repository. One operator, one small host, Python.

## Headline findings

* All three engines have a current, officially maintained Python SDK. Hatchet and Temporal ship Python releases every two to three weeks. Inngest's Python SDK last stable release was June 2026 with an alpha in September, and Inngest says TypeScript gets features first.
* The human approval wait is covered by a documented primitive in all three: Hatchet `ctx.aio_wait_for_event`, Inngest `step.wait_for_event`, Temporal `@workflow.signal` plus `workflow.wait_condition`. None of the three charges for idle time as such. Inngest Cloud free tier caps the whole run, waits included, at 30 days, and Hatchet documents no cap at all (the cap is UNVERIFIED, not confirmed absent).
* Per key concurrency with two keys at once ("at most N per project" and "at most 1 per repository") is a documented, declarative feature in Hatchet (list of `ConcurrencyExpression`) and Inngest (up to two `inngest.Concurrency` entries). Temporal has no server side per key concurrency; the community answer is a hand written mutex workflow. That is the one finding that would push the decision away from Temporal.
* Inbound webhooks: Hatchet and Inngest host an inbound endpoint that turns a GitHub webhook into an event. Temporal exposes an HTTP API on the frontend (port 7243) but the signal route is UNVERIFIED from official docs, so Phactory would run its own endpoint.
* The Claude Code CLI documents headless use with a subscription through `claude setup-token` and `CLAUDE_CODE_OAUTH_TOKEN`. The legal page says OAuth is for "ordinary use of Claude Code," that developers building products should use API keys, and that Anthropic may enforce without notice. A single operator running the unmodified binary with their own subscription is explicitly allowed. Sustained factory volume may not read as "ordinary individual usage." This is a policy risk, not a technical block.

## Engine by engine

### Hatchet

1. Python SDK. Package `hatchet-sdk`, described on PyPI as "the official Python SDK for Hatchet." Latest 1.42.1 uploaded 2026-10-09, with 1.41.0 on 2026-09-22 and 1.42.0 the same day as 1.42.1. Requires Python >=3.10, <4. PRIMARY: https://pypi.org/pypi/hatchet-sdk/json (queried directly). The repo README says Hatchet "supports applications written in Python, TypeScript, Go and Ruby." PRIMARY: https://github.com/hatchet-dev/hatchet. Python is a first class SDK, not a port. The durable event wait docs show Python first alongside TypeScript, Go and Ruby. PRIMARY: https://docs.hatchet.run/v1/durable-event-waits

2. Durable wait for an external event. Primitive: `await ctx.aio_wait_for_event("event:key", expression="input.pr_id == '42'")` inside a durable task, with a CEL filter and an optional `lookback_window=timedelta(...)` plus a scope to catch events that arrived just before the wait started. On interruption: "If a task is interrupted and requeued while waiting, the event will still be processed," read back from the durable event log. PRIMARY: https://docs.hatchet.run/v1/durable-event-waits. While waiting, "Hatchet can evict it and free the worker slot," so a worker restart mid wait does not lose the wait. PRIMARY: https://docs.hatchet.run/v1/durable-tasks. Maximum wait duration: UNVERIFIED. Neither the event wait page, the durable sleep page, nor the engine configuration page states a cap. The `execution_timeout` default is 60s on ordinary tasks, and the docs do not say whether it bounds a durable wait. PRIMARY: https://docs.hatchet.run/home/timeouts. Cost while idle: Hatchet Cloud meters task runs and events, not wall clock time, so a waiting run is still one run. Inference from the pricing page, which does not say either way. PRIMARY: https://hatchet.run/pricing

3. Durable sleep. `await ctx.aio_sleep_for(timedelta(...))`. "Guaranteed to respect the original duration across interruptions of the durable task, worker crashes, and so on." "While the task is sleeping, no resources are consumed, and the task can also be evicted in order to free the worker slot." Max duration: not stated, UNVERIFIED. PRIMARY: https://docs.hatchet.run/v1/durable-sleep. Waits can be combined with "or groups" so a sleep and an event wait race, which is the polling fallback shape Phactory needs. PRIMARY: https://docs.hatchet.run/home/durable-execution

4. Per key concurrency. Feature name: Concurrency, via `ConcurrencyExpression(expression="input.project", max_runs=N, limit_strategy=ConcurrencyLimitStrategy.GROUP_ROUND_ROBIN)`. "You can also combine multiple concurrency strategies," by passing a list to `concurrency=`, so one workflow can declare `input.project` at N and `input.repository` at 1 together. Shared strategies across workflows and expression based `max_runs` need engine 0.106.0 or later. PRIMARY: https://docs.hatchet.run/home/concurrency

5. Self hosting footprint. Components: API server, engine, PostgreSQL, optional RabbitMQ, dashboard. No Redis, no ClickHouse. PRIMARY: https://docs.hatchet.run/self-hosting. The `hatchet-lite` image bundles engine and API in one container next to a `postgres:15.6` service, with Postgres doing double duty as the message queue; two services total. "Designed for development and low-volume use-cases." PRIMARY: https://docs.hatchet.run/self-hosting/hatchet-lite. The full compose runs postgres, rabbitmq, migration, setup-config, hatchet-engine, hatchet-dashboard, and RabbitMQ can be dropped with `SERVER_MSGQUEUE_KIND=postgres`. No CPU or RAM sizing given. PRIMARY: https://docs.hatchet.run/self-hosting/docker-compose. License MIT. PRIMARY: https://github.com/hatchet-dev/hatchet. Hosted free tier as of today: without a card, 2,000 task runs per day, 2,000 events per day, 10 workers, 1 tenant, 3 users, 1 day retention. With a card on file, 1M runs and 1M events per month included, then $30 per million runs and $5 per million events, 100 workers, 10 tenants, 50 users, 7 day retention. The earlier pass's "free 1M runs" is the card on file tier. PRIMARY: https://hatchet.run/pricing

6. Webhook ingestion. Hatchet hosts the inbound endpoint. URL shape `.../api/v1/stable/tenants/<tenant-id>/webhooks/<webhook-name>`. GitHub, Stripe and Slack are pre configured sources needing only the webhook secret; generic sources take Basic, API key, or HMAC auth. A CEL expression over `input` and `headers` becomes the event key, and workflows subscribe through `on_events` or a durable event wait. PRIMARY: https://docs.hatchet.run/home/webhooks. Self hosted engines carry `SERVER_INCOMING_WEBHOOK_RATE_LIMIT` (default 50/s) and `SERVER_LIMITS_DEFAULT_INCOMING_WEBHOOK_LIMIT` (default 5 webhooks), which indicates the feature exists off Cloud. PRIMARY: https://docs.hatchet.run/self-hosting/configuration-options. Whether the self hosted route is identical: UNVERIFIED. Phactory can also push events from its own endpoint through the SDK.

7. Versioning. Hatchet replays the durable event log on resume, so "the code between checkpoints must be reproducible on replay." Temporal style patching: "Hatchet has no equivalent." Guidance: "deploying a new durable task definition and letting the old work drain." PRIMARY: https://docs.hatchet.run/v1/from-temporal-to-hatchet. So a run that has waited three days resumes under whatever code is deployed; if the path to its checkpoint changed, it can diverge. Keep the durable task tiny (dispatch, wait, verify as child tasks) so the replayed path rarely changes.

8. Cron. `hatchet.workflow(name=..., on_crons=["*/15 * * * *"])`, or dynamic `aio_create_cron(...)`. UTC only, missed schedules not backfilled, concurrency policy still applies. PRIMARY: https://docs.hatchet.run/home/cron-runs

### Inngest

1. Python SDK. Package `inngest`. Latest stable 0.5.19 uploaded 2026-06-23; 0.5.20a0 pre release on 2026-09-29; requires Python >=3.10. Classifier "Production/Stable." PRIMARY: https://pypi.org/pypi/inngest/json (queried directly). The SDKs page: "TypeScript gets new features first" and "The examples in these docs use TypeScript unless a page says otherwise." Feature table marks Python as supported for wait for event, sleep and sleep until, cron triggers, Connect workers; wait for signal is "not supported yet" in Python. PRIMARY: https://www.inngest.com/docs/sdks. The Python reference says "Some features are TypeScript-only for now" and marks the `@step` decorator experimental. PRIMARY: https://www.inngest.com/docs/reference/python. Verdict: maintained, but a second tier SDK by the vendor's own words.

2. Durable wait for an external event. `await ctx.step.wait_for_event("wait-for-merge", event="github/pull_request.merged", if_exp="event.data.pr_id == async.data.pr_id", timeout=datetime.timedelta(days=7))`, returns `None` on timeout. The wait "only sees events sent after it starts listening." PRIMARY: https://www.inngest.com/docs/features/inngest-functions/steps-workflows/wait-for-event. Max timeout: not stated as its own number; the whole run, "including sleeps and waits," must finish inside the plan's max run length: 30 days Free, 90 days Pro, 366 days Business. PRIMARY: https://www.inngest.com/docs/usage-limits/inngest. Worker restart: Inngest "resumes the run without keeping your function process running while it waits," and injects saved state into a new execution, so the worker is not involved in the wait. PRIMARY: https://www.inngest.com/docs/learn/how-functions-are-executed. Cost while idle: executions are "metered per function run and per step inside that run," formula `runs × (steps + 1)`; the pricing page does not say whether a waiting step is charged, so UNVERIFIED for the wait specifically, but there is no time based charge. PRIMARY: https://www.inngest.com/pricing

3. Durable sleep. `await ctx.step.sleep("id", timedelta(...))` and `sleep_until`. "A sleep can last up to one year," bounded by the plan's max run length. "Sleeping runs do not count toward account or function concurrency limits." PRIMARY: https://www.inngest.com/docs/features/inngest-functions/steps-workflows/sleeps

4. Per key concurrency. Feature name: Concurrency. `concurrency=[inngest.Concurrency(limit=N, key="event.data.project"), inngest.Concurrency(limit=1, key="event.data.repository")]`. "A function can have up to two concurrency constraints," and a step starts only when it fits both. Note the Inngest limit is on concurrently running steps, not runs, and the Free plan caps total concurrent steps at 5 across the account. PRIMARY: https://www.inngest.com/docs/guides/concurrency and https://www.inngest.com/pricing

5. Self hosting footprint. One binary, `inngest start`, with embedded in memory Redis and SQLite by default; external Postgres and Redis are optional via `--postgres-uri` and `--redis-uri`. A three service compose (inngest, postgres:17, redis:7) is documented. `inngest start` is labelled "[Beta]." "Inngest's support team does not guarantee direct support for self-hosted instances." The server "does not automatically delete old database rows," so retention is on you. PRIMARY: https://www.inngest.com/docs/self-hosting. License: "Server Side Public License and delayed open source publication (DOSP) under Apache 2.0" for server and CLI; SDKs Apache 2.0. PRIMARY: https://github.com/inngest/inngest. Hosted free tier today: 50k executions per month, 5 concurrent steps, 3 workers, 24 hour trace history, 30 day max run length, no overage (execution pauses at quota). Pro from $99 per month. PRIMARY: https://www.inngest.com/pricing. Whether the 30 day run cap applies to a self hosted server: UNVERIFIED.

6. Webhook ingestion. Inngest Cloud hosts a webhook URL per source; a JavaScript transform on Inngest's servers turns the payload into an event name and data. "Inngest does not verify provider webhook signatures," so the function must verify GitHub's signature itself before side effects. PRIMARY: https://www.inngest.com/docs/platform/webhooks. Whether self hosted Inngest runs webhook transforms: UNVERIFIED (not stated in the self hosting docs). Alternative: Phactory's own endpoint calls `inngest.send(...)`.

7. Versioning. "You can deploy new function code while runs are waiting or sleeping." Memoization is by step ID: completed steps return saved results, added steps run when reached, a changed ID is treated as a new step and runs again, reordering only logs a warning. No determinism errors, no patch API needed. PRIMARY: https://www.inngest.com/docs/learn/versioning. This is the friendliest redeploy story of the three for a run that has waited three days.

8. Cron. `trigger=inngest.TriggerCron(cron="*/15 * * * *")`, optional `jitter`, `TZ=` prefix for local time, UTC by default. PRIMARY: https://www.inngest.com/docs/guides/scheduled-functions

### Temporal

1. Python SDK. Package `temporalio`. Latest 1.34.0 uploaded 2026-09-30, with 1.31 through 1.33 landing monthly before it. Requires Python >=3.10. PRIMARY: https://pypi.org/pypi/temporalio/json (queried directly). Python is one of Temporal's first party SDKs with its own full docs tree. PRIMARY: https://docs.temporal.io/develop/python/core-application. No deprecation notice; the sandbox module is marked "not yet considered stable." PRIMARY: https://pypi.org/project/temporalio/

2. Durable wait for an external event. Primitives: `@workflow.signal` handler sets state, then `await workflow.wait_condition(lambda: self.merged, timeout=...)`. Client side: `await handle.signal(Workflow.merged, payload)`. Signals are durable server side. PRIMARY: https://docs.temporal.io/develop/python/message-passing. Limits: a Workflow Execution can receive up to 10,000 Signals; Event History caps at 51,200 events or 50 MB; timers up to 100 years; no stated max execution duration. PRIMARY: https://docs.temporal.io/cloud/limits. Worker restart mid wait: workflow state is rebuilt from Event History on the next Worker, which is the core of the model. PRIMARY: https://docs.temporal.io/develop/python/versioning (determinism and replay). Cost while idle on Cloud: every Signal and every Timer start is an Action; an idle open workflow accrues no Actions but counts as Active Storage at $0.042 per GB hour. PRIMARY: https://docs.temporal.io/cloud/actions and https://docs.temporal.io/cloud/pricing

3. Durable sleep. `await asyncio.sleep(seconds)` inside the workflow. "Timers are persisted, so even if your Worker or Temporal Service is down when the time period completes" the sleep resolves on recovery. "A Workflow can sleep for months." PRIMARY: https://docs.temporal.io/develop/python/timers. Max 100 years. PRIMARY: https://docs.temporal.io/cloud/limits

4. Per key concurrency. Not a documented server feature. The Temporal community answer is a "mutex workflow": one long lived workflow per resource, other workflows signal it for a turn, with a known trap that signals can be lost across continue as new. THIRD PARTY: https://community.temporal.io/t/limit-workflow-based-concurrent-executions/633 and https://community.temporal.io/t/how-to-synchronize-workflow-resources-in-python-sdk/15258. I found no docs.temporal.io page offering per key limits. Phactory would be writing and testing its own landing lock, which is the exact state file logic the plan decided to stop hand writing.

5. Self hosting footprint. Dev server `temporal server start-dev --db-filename state.db` is a single binary with SQLite and bundled UI, but "The development server is not intended for production use" and "skips certain HTTP security checks." PRIMARY: https://docs.temporal.io/cli/server. The documented compose (temporalio/samples-server, `compose/`) "includes a PostgreSQL database, an Elasticsearch instance," plus the server and UI; a Postgres only variant exists. PRIMARY: https://docs.temporal.io/self-hosted-guide/deployment. The older temporalio/docker-compose repo is archived and warns that its auto-setup image is not for production. PRIMARY: https://github.com/temporalio/docker-compose. Cloud pricing: Developer plan "greater of $0/month or 10% of your Temporal Cloud consumption," $50 per million Actions, Active Storage $0.042 per GB hour, Retained $0.00105 per GB hour. No free tier or trial credit amount stated. PRIMARY: https://docs.temporal.io/cloud/pricing

6. Webhook ingestion. Temporal does not host a GitHub style webhook endpoint. Since server 1.22 "The frontend workflow service API can now exposed via HTTP in addition to the existing gRPC exposed form," port 7243 in the default Docker template, with routes defined by proto annotations. PRIMARY: https://github.com/temporalio/temporal/releases/tag/v1.22.0. Whether signal is exposed on that HTTP API and at what path: UNVERIFIED from official docs; a third party profile says it is. THIRD PARTY: https://github.com/api-evangelist/temporal-io. Practical answer: Phactory runs its own small HTTP endpoint that verifies GitHub's signature and calls `handle.signal(...)` with the Python client.

7. Versioning. "The Temporal Platform requires that Workflow code is deterministic." A run waiting three days that is resumed under changed orchestration code fails its Workflow Task with a non determinism error unless the change is guarded with `workflow.patched("id")`, later `deprecate_patch`, or Workers are deployed with Worker Versioning so old runs pin to old code. Sunset note: "Support for the experimental Worker Versioning method before 2025 will be removed from Temporal Server in March 2026," so only the current Worker Deployment Versions flavour counts. PRIMARY: https://docs.temporal.io/develop/python/versioning. This is the heaviest redeploy discipline of the three.

8. Cron. Use Schedules: `client.create_schedule(id, Schedule(action=ScheduleActionStartWorkflow(...), spec=ScheduleSpec(cron_expressions=[...])))`. "We recommend using Schedules instead of Cron Jobs"; the legacy `cron_schedule` start option still exists but is not the recommended path. Each Schedule execution costs three Actions on Cloud. PRIMARY: https://docs.temporal.io/develop/python/schedules and https://docs.temporal.io/cloud/actions

## Sandboxes for the headless builder

### Daytona

Sandboxes are created from the Python SDK (`daytona` package, 0.224.1 uploaded 2026-10-14, PRIMARY: https://pypi.org/pypi/daytona/json) with `daytona.create(CreateSandboxFromImageParams(image="ghcr.io/you/builder:1.2"))` for any public image with a tag or digest (`latest` rejected), or from a snapshot built via `daytona.snapshot.create(CreateSnapshotParams(name=..., image=...))` or a Dockerfile through the CLI; local images must be AMD64. PRIMARY: https://www.daytona.io/docs/en/sandboxes and https://www.daytona.io/docs/en/snapshots. Defaults are 1 vCPU, 1 GB RAM, 3 GiB disk, with organization maximums of 4 vCPU, 8 GB, 10 GB. Lifetime: auto stop after 15 minutes idle by default (0 disables), auto archive after 7 days stopped by default with a 30 day maximum, no auto delete and no wall clock TTL unless set, so a sandbox can live indefinitely. Stopping "preserves the filesystem, but memory state is not," archiving moves the filesystem to object storage and "Start the sandbox again when you need to use it." PRIMARY: https://www.daytona.io/docs/en/sandboxes.md. Persistent login: the filesystem (and so a `~/.claude` directory under `CLAUDE_CONFIG_DIR`) survives stop, start and archive, and a snapshot "from a running or stopped sandbox" captures filesystem state for container sandboxes; the docs do not say anything about login sessions, so carrying a Claude login this way is plausible but UNVERIFIED. Volumes are S3 backed FUSE mounts, "generally slower," free, and a poor fit for a working git clone. PRIMARY: https://www.daytona.io/docs/en/volumes. Cost: $0.0504 per vCPU hour, $0.0162 per GiB RAM hour, $0.000108 per GiB disk hour, per second billing, $200 free compute on pay as you go. A 2 vCPU, 4 GiB, 8 GiB sandbox is about $0.17 per hour running, disk only when stopped, nothing when archived. PRIMARY: https://www.daytona.io/pricing and https://www.daytona.io/docs/en/billing

### Plain VPS with Docker

A DigitalOcean Basic droplet is $4 per month ($0.00595 per hour) for 1 vCPU and 512 MiB, $6 ($0.00893 per hour) for 1 GiB, $12 ($0.01786 per hour) for 2 GiB. PRIMARY: https://www.digitalocean.com/pricing/droplets. Hetzner's cloud page did not render prices for me, UNVERIFIED. On a VPS, Phactory creates containers from any image through the Docker Engine API, they live until removed, and a named volume mounted at `~/.claude` with `CLAUDE_CONFIG_DIR` pointing at it keeps the login across container rebuilds; that mount pattern is the one Anthropic documents for dev containers. PRIMARY: https://code.claude.com/docs/en/devcontainer. I did not fetch the Docker Engine API or volumes docs this pass, so those two mechanics are stated from general knowledge and marked UNVERIFIED for this document. The trade: a $12 VPS running both the engine and two or three builder containers is far cheaper than Daytona per hour, but Phactory owns image builds, cleanup, and host isolation, and a runaway builder shares the host with the control loop.

### Claude Code CLI headless with a subscription

Official docs: `claude -p "..."` runs non interactively; `--permission-prompts none` and `--permission-mode` handle unattended runs; `--bare` is the recommended scripted mode but "doesn't use your subscription login," so a subscription run must not pass `--bare`. PRIMARY: https://code.claude.com/docs/en/headless. `claude setup-token` mints a one year OAuth token for `CLAUDE_CODE_OAUTH_TOKEN`, "for CI pipelines, scripts, or other environments where interactive browser login isn't available," and "requires a Pro, Max, Team, or Enterprise plan." It can only make model requests, and bare mode does not read it. PRIMARY: https://code.claude.com/docs/en/authentication. In a container, mount a volume at `~/.claude` and set `CLAUDE_CONFIG_DIR` to the same path, or pass `CLAUDE_CODE_OAUTH_TOKEN` as a secret; `--dangerously-skip-permissions` is refused as root. PRIMARY: https://code.claude.com/docs/en/devcontainer. Policy, quoted from the legal page: "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK." "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code." "Developers building products or services ... should use API key authentication." And: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code." "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice." PRIMARY: https://code.claude.com/docs/en/legal-and-compliance. Usage limits are shared between claude.ai and Claude Code. PRIMARY: https://support.claude.com/en/articles/11145838-using-claude-code-with-your-pro-or-max-plan. Reports of enforcement against third party harnesses using subscription tokens in early 2026 are THIRD PARTY and not confirmed against an Anthropic page: https://alternativeto.net/news/2026/2/anthropic-officially-bans-using-subscription-authentication-for-third-party-claude-use. Read: one operator, own subscription, unmodified CLI, is inside the rules today; a factory that burns the weekly limit nightly is the thing the "ordinary individual usage" sentence is about, and the fallback is `ANTHROPIC_API_KEY`, which the CLI prefers over the subscription in `-p` mode whenever it is set.

## Does the durable engine decision hold?

Yes, with one qualifier. Hatchet and Inngest both give Phactory the four things the loop needs declaratively: a durable event wait with a per run filter, a durable sleep to race it, two concurrent per key limits, and a hosted inbound webhook. Temporal gives the first two and makes Phactory write the third and host the fourth, plus the strictest redeploy rules. The qualifier: nobody documents a maximum wait for Hatchet, Inngest Cloud free caps a run at 30 days, and Phactory's "hours to days" wait has no documented upper bound of its own, so the workflow needs a deadline step (give up, reschedule, or escalate) rather than an open ended wait.

## Recommendation

Engine: Hatchet, self hosted with the `hatchet-lite` image and one Postgres on the same VPS, moving to the full compose only if throughput demands it. It is MIT, Postgres only, and the only candidate where Python is first tier, two key concurrency is declarative, and GitHub webhooks land in the engine without Phactory hosting an endpoint.
SDK: `hatchet-sdk` 1.42.x, durable tasks with `aio_wait_for_event` or grouped with `aio_sleep_for` for the polling fallback.
Sandbox: start with Docker on the same VPS (named volume at `~/.claude`, `CLAUDE_CONFIG_DIR` set, token from `claude setup-token`), and move builders to Daytona snapshots when isolation or host contention bites, since Daytona's API, lifecycle and per hour cost are all documented.
Spike to prove in one day: start a durable task that waits on a real GitHub `pull_request.merged` webhook delivered to the self hosted Hatchet webhook URL, kill and restart the worker and the engine container while it waits, redeploy the worker with a trivial code change, then merge the PR and confirm the run resumes and completes, with a second run on the same repository key held at `max_runs=1` the whole time. If the self hosted webhook route or the resume after redeploy fails, fall back to Inngest self hosted with Phactory's own webhook endpoint.
